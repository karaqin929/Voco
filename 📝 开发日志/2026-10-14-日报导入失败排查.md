# 开发日志 2026-10-14 附：GPT 日报导入失败深度排查报告

用户 2026-10-14 报告：粘贴 GPT 生成日报到 Voco 导入，显示「格式错误：JSON 语法不合法，无法解析（详情见控制台）」。连续质疑：① 上次修出 bug 了？② 是上个版本 prompt 改坏了？③ 是不是加入 transcript 让模板变长导致的？——本文用实测 + git 取证逐一回答。

## 结论先行

1. **上次改了什么**：v128→v129 模板净增 824 字符，全部改动集中在「占比计算 / transcript / 斜杠禁令」，**零处涉及数组方括号**；解析代码侧 3 处改动全部是新增功能，报错路径一字未动。
2. **为什么日报出错**：GPT 生成的 JSON 有 **5 处数组漏了方括号**（43 个元素「裸奔」），`JSON.parse` 在第 457 字符处（第一个数组的第 2 个元素后）必然失败；App 拒收是正确行为。另有一处次级缺陷：一条 expression 错题的 `pattern` 被填成了语法类别的枚举值「句式与搭配」。
3. **是否上次改动导致**：**不是**。决定性证据——用 v128 旧代码（c31e736，上次改动前）解析这份一模一样的日报，**报错一字不差**。报错发生在新旧版本都从未改动的 `JSON.parse` 环节，与 v129 的 transcript 改动没有任何交集。

## 一、报了什么错（用线上同版代码实测复现）

把用户贴的日报原文（11977 字符）喂给 App 真实解析链 `sanitizeJsonInput → normalizeSmartQuotes → JSON.parse`：

- `JSON.parse` 失败：`SyntaxError: Expected ':' after property name in JSON at position 457`
- 失败位置上下文：`"strengths": "能够主动开启和延续日常对话…", "能够描述复杂的个人感受…", "能够使用条件…` —— strengths 数组第 1 个元素是裸字符串，第 2 个元素跟着逗号出现，解析器把它当成属性名等 `:` 失败。
- `validateImportInput` 返回：`status: error`，`error: 格式错误：JSON 语法不合法，无法解析（详情见控制台）` —— 与用户看到的一字不差。

## 二、结构缺陷全表（normalizeSmartQuotes 后逐字段走查）

| 键 | 位置 | 方括号壳 | 元素数 |
|---|---|---|---|
| summary.strengths | @385 | ❌ 无 | 4 |
| summary.nextSteps | @607 | ❌ 无 | 2 |
| mistakes | @849 | ❌ 无 | 12 |
| coreSentences | @4769 | ❌ 无 | 14 |
| newWords | @9568 | ❌ 无 | 11 |

共 **5 个数组、43 个元素**全部「裸奔」（键后直接跟元素、逗号分隔，没有 `[ ]`）。

**迭代修复验证**：按顺序手工补上 5 对方括号（strengths → nextSteps → mistakes → coreSentences → newWords）后，`JSON.parse` 立即成功——**证明除这 5 处漏壳外，整份 JSON 结构完全合法**。对象 `{}`、键名、键值、嵌套层级全对，唯独数组壳掉了。

**次级缺陷**（同样与模板改动无关）：@4080 处一条 `type: "expression"` 的错题，`pattern` 被填成 `"句式与搭配"`——这是 `category` 字段的枚举值（语法错题专用），串进了 `pattern` 字段（只允许 直译语序/用词搭配/冗余啰嗦/表达习惯 四个值）。即该条数据即使解析成功也会在归一化时被归类兜底。属于生成质量劣化的另一表现。

## 四、为什么不是上次改动导致的（证据链）

1. **旧代码同样拒收**：用 c31e736（v128，上次改动前）的 `validateImportInput` 解析同一份日报 → 同样 `JSON.parse` 在 position 457 失败、同样返回「格式错误：JSON 语法不合法，无法解析」——一字不差。旧版本照样报这个错，与「改坏了」无关。
2. **报错发生在新旧版本都未改动的环节**：失败点是 `JSON.parse` 本身，两版 diff 证明该路径零改动；v129 所有新逻辑（countTranscriptRatio 等）的触发条件是 `transcript` 存在——**这份日报没有 transcript**（顶层正好 6 键），新代码一条都执行不到。
3. **方括号两版模板都有要求**：见 3.1 对照，GPT 漏写 ≠ 模板没要求。用户若用的是 v129 新模板，则 GPT 同时犯了两项违规（漏掉 transcript 键 + 5 处数组漏壳）；若还是旧模板，数组漏壳同样违规。无论哪个版本模板，这份日报都过不了。
4. **漏壳是长输出生成缺陷，不是指令缺陷**：这份日报 11977 字符、43 个数组元素 + 大段 explanation，而对象 `{}`、键名、键值全部正确——唯独 5/5 的数组掉了壳。这是 LLM 在超长结构化输出上的已知失败模式（数组语法令牌注意力漂移），与 prompt 内容无关。
5. **「transcript 变长导致出错」不成立**：模板确实 +824 字符（+14%），但这份日报**连 transcript 都没有生成**——如果 GPT 因指令过长而吃力，它的表现是省略最重的字段（恰恰发生在 transcript 上），而漏方括号是语法级缺陷，旧模板（无 transcript 要求）同样可能发生。用旧模板生成同样结构，照样报错。
6. **pattern 串位佐证**：「句式与搭配」漏进 pattern 字段说明该次生成整体质量劣化——铁律里两个枚举都写得清清楚楚，GPT 仍然串位。与漏壳同源，均为生成侧失误。

## 五、建议（未实施，待确认）

1. **App 侧兜底**（推荐）：`sanitizeJsonInput` 里检测「键后裸字符串/裸对象序列」（本报告的结构走查器已验证该算法可行），自动补 `[ ]` 后再 `JSON.parse`——旧模板用户、任何模型偶发掉壳都能救回。加 smoke S10 守门。
2. **模板自检加一条**：「五个数组（strengths/nextSteps/mistakes/coreSentences/newWords）必须带方括号 [ ]」。
3. 不改的话：换模板前用户仍会偶发踩雷，属已知生成缺陷，拒收即保护数据完整。
